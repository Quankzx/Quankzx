Chương 1: 4 Trụ Cột OOP & 5 Nguyên Lý SOLID Thực Tế

Câu 1: Trình bày 4 tính chất cơ bản của lập trình hướng đối tượng (OOP) và cho ví dụ C#?
▼
🎯 Người phỏng vấn muốn kiểm tra: Kiến thức nền tảng về tư duy lập trình đối tượng.
  • 1. Encapsulation (Đóng gói): Gom nhóm dữ liệu và phương thức xử lý dữ liệu vào trong một Class, đồng thời che giấu trạng thái bên trong thông qua access modifiers (private, protected, public) và dùng Properties (get/set) để kiểm soát việc thay đổi dữ liệu.
  • 2. Abstraction (Trừu tượng hóa): Ẩn đi các chi tiết cài đặt phức tạp, chỉ hiển thị những tính năng cần thiết cho bên ngoài thông qua interface hoặc abstract class (ví dụ: client chỉ gọi IPaymentService.ProcessPayment() mà không cần biết bên dưới gọi Stripe hay PayPal).
  • 3. Inheritance (Kế thừa): Cho phép một class con tái sử dụng các thuộc tính và phương thức từ class cha (ví dụ: SettlementSyncWorker kế thừa BackgroundService).
  • 4. Polymorphism (Đa hình): Một hành vi có thể được thực thi theo nhiều cách khác nhau tại thời điểm runtime (thông qua virtual/override method hoặc triển khai interface).
Câu 2: SOLID là viết tắt của những nguyên lý nào? Trình bày chi tiết từng nguyên lý và cách áp dụng trong C#?
▼
🎯 Người phỏng vấn muốn kiểm tra: Khả năng viết code sạch, dễ mở rộng, dễ bảo trì theo chuẩn Enterprise.
SOLID là 5 nguyên lý thiết kế hướng đối tượng cốt lõi:
  • S - Single Responsibility Principle (SRP): Một Class chỉ nên có một lý do duy nhất để thay đổi.
    Ví dụ: Tách riêng OrderService (chỉ xử lý nghiệp vụ đơn hàng), InvoiceGenerator (chỉ tạo hóa đơn PDF), và EmailService (chỉ gửi mail).
  • O - Open/Closed Principle (OCP): Mở cho việc mở rộng (Open for extension) nhưng Đóng cho việc sửa đổi (Closed for modification).
    Ví dụ: Khi thêm phương thức thanh toán mới (VNPay, Momo), ta tạo thêm class mới kế thừa IPaymentMethod thay vì sửa chuỗi switch-case trong code cũ.
  • L - Liskov Substitution Principle (LSP): Các đối tượng của class con phải có thể thay thế cho class cha mà không làm hỏng tính đúng đắn của chương trình.
    Ví dụ: Class con không được throw NotImplementedException đối với các phương thức của class cha.
  • I - Interface Segregation Principle (ISP): Không nên ép client phải phụ thuộc vào các interface mà họ không sử dụng. Thay vì tạo một "Fat Interface" lớn với 20 method, hãy tách thành nhiều interface nhỏ chuyên biệt (ví dụ: IReadOnlyRepository và IWriteRepository).
  • D - Dependency Inversion Principle (DIP): Các module cấp cao không nên phụ thuộc vào module cấp thấp; cả hai nên phụ thuộc vào Abstraction (Interface).
Câu 3: Tại sao các kỹ sư thường khuyên: "Ưu tiên Composition hơn Inheritance" (Favor Composition over Inheritance)?
▼
🎯 Người phỏng vấn muốn kiểm tra: Tư duy linh hoạt trong thiết kế kiến trúc phần mềm.
  • Nhược điểm của Kế thừa (Inheritance): Tạo ra sự liên kết chặt chẽ (Tight Coupling). Mọi thay đổi ở class cha có thể làm hỏng hành vi của hàng loạt class con (Fragile Base Class problem), và C# không hỗ trợ đa kế thừa class.
  • Ưu điểm của Composition (HAS-A thay vì IS-A): Class chứa tham chiếu đến các Interface/Component khác thông qua Dependency Injection. Giúp dễ dàng thay đổi hành vi tại runtime, dễ mock để viết Unit Test và giảm thiểu sự phụ thuộc cứng nhắc.
Câu 4: Sự khác biệt giữa Abstract Class và Interface trong C#? Khi nào nên dùng loại nào?
▼
  • Interface: Định nghĩa một "bản hợp đồng" (Contract) về hành vi (CAN-DO). Một class có thể triển khai nhiều interface. Không chứa trạng thái (fields) và thích hợp để Decouple giữa các tầng kiến trúc.
  • Abstract Class: Định nghĩa một kiểu danh tính dùng chung (IS-A) cho các class có mối quan hệ họ hàng mật thiết. Có thể chứa trạng thái (fields), constructor, access modifiers, và các phương thức có sẵn code triển khai (concrete methods). Một class chỉ có thể kế thừa duy nhất 1 abstract class.
  • Quy tắc: Dùng Interface cho Dependency Injection và đa hình hành vi; dùng Abstract Class khi các class con thực sự chia sẻ chung nhiều code xử lý nền tảng.

Chương 2: Inversion of Control (IoC), DI & Design Patterns

Câu 5: Phân biệt Inversion of Control (IoC), Dependency Injection (DI) và Dependency Inversion Principle (DIP)?
▼
🎯 Người phỏng vấn muốn kiểm tra: Khả năng phân biệt rõ ràng giữa Nguyên lý (Principle), Mẫu thiết kế (Pattern) và Framework (IoC Container).
  • DIP (Dependency Inversion Principle): Là một Nguyên lý thiết kế (trong SOLID), nói rằng: Module cấp cao không phụ thuộc module cấp thấp, cả hai cùng phụ thuộc vào Interface.
  • IoC (Inversion of Control): Là một Khái niệm/Mô hình kiến trúc đảo ngược luồng điều khiển của ứng dụng (Framework tự gọi code của bạn thay vì code của bạn kiểm soát toàn bộ luồng thực thi).
  • DI (Dependency Injection): Là một Design Pattern cụ thể để hiện thực hóa IoC và DIP, bằng cách "tiêm" (inject) các phụ thuộc (dependencies) từ bên ngoài vào class (qua Constructor, Method, hoặc Property) thay vì class tự dùng từ khóa new để tạo đối tượng.
Câu 6: Service Locator Pattern là gì và tại sao nó bị coi là một Anti-Pattern?
▼
Service Locator: Là pattern sử dụng một đối tượng trung tâm (như IServiceProvider) để trực tiếp gọi serviceProvider.GetService<T>() bên trong các hàm nghiệp vụ.

Tại sao là Anti-Pattern:
  • Che giấu sự phụ thuộc (Hidden Dependencies): Nhìn vào constructor của class, ta không thể biết class đó thực sự cần những service nào để hoạt động.
  • Khó viết Unit Test: Khi test, ta phải mock cả Service Locator thay vì chỉ mock các interface cần thiết.
  • Dễ gây lỗi Runtime: Nếu thiếu đăng ký service trong DI, lỗi chỉ phát sinh khi chạy tới dòng code đó (Runtime Exception) thay vì được phát hiện ngay khi khởi tạo class.
Câu 7: Làm thế nào để triển khai Thread-Safe Singleton Pattern trong C# chuẩn nhất?
▼
Cách chuẩn nhất và hiện đại nhất trong .NET là sử dụng System.Lazy<T>: 
public sealed class DatabaseConnectionPool
{
    private static readonly Lazy<DatabaseConnectionPool> _instance =
        new Lazy<DatabaseConnectionPool>(() => new DatabaseConnectionPool(), LazyThreadSafetyMode.ExecutionAndPublication);

    private DatabaseConnectionPool() { /* Khởi tạo kết nối */ }

    public static DatabaseConnectionPool Instance => _instance.Value;
}
Ưu điểm: Đảm bảo 100% Thread-Safe, chỉ khởi tạo khi thực sự được truy cập lần đầu tiên (Lazy Loading), và hiệu năng cao hơn nhiều so với việc dùng khối lock truyền thống (Double-Check Locking).
Câu 8: Strategy Pattern giải quyết bài toán gì và em áp dụng nó như thế nào để thay thế các câu lệnh if-else / switch-case phức tạp?
▼
Strategy Pattern định nghĩa một tập hợp các thuật toán/nghiệp vụ, đóng gói từng thuật toán vào một class riêng biệt và cho phép hoán đổi chúng linh hoạt tại runtime.

Ứng dụng thực tế: Xử lý chiết khấu hoặc tính phí vận chuyển theo từng sàn TMĐT:
  1. Tạo interface IShippingCalculator với phương thức CalculateFee(Order order).
  2. Tạo các class triển khai: AmazonShippingCalculator, ShopeeShippingCalculator, StandardShippingCalculator.
  3. Đăng ký tất cả vào DI Container. Khi cần tính phí, một Factory/Dictionary sẽ dựa vào loại đơn hàng để lấy đúng Strategy tương ứng mà không cần viết chuỗi if-else dài dặc, tuân thủ tuyệt đối Open/Closed Principle.
Câu 9: Decorator Pattern là gì? Cho ví dụ ứng dụng trong việc gắn Caching hoặc Logging vào Service?
▼
Decorator Pattern cho phép thêm hành vi mới vào một đối tượng một cách linh hoạt mà không cần sửa đổi mã nguồn của class gốc hoặc dùng kế thừa.

Ví dụ: Gắn Caching cho IProductService: 
public class CachedProductService : IProductService
{
    private readonly IProductService _inner;
    private readonly IMemoryCache _cache;

    public CachedProductService(IProductService inner, IMemoryCache cache)
    {
        _inner = inner;
        _cache = cache;
    }

    public async Task<Product> GetByIdAsync(int id)
    {
        return await _cache.GetOrCreateAsync($"product-{id}", entry =>
        {
            entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10);
            return _inner.GetByIdAsync(id);
        });
    }
}
Câu 10: Options Pattern trong .NET hoạt động ra sao? Phân biệt IOptions, IOptionsSnapshot và IOptionsMonitor?
▼
Options Pattern ánh xạ các section trong file cấu hình (appsettings.json) thành các class C# strongly-typed:
  • IOptions<TOptions>: Đăng ký dạng Singleton. Giá trị cấu hình được đọc một lần duy nhất lúc ứng dụng khởi động. Không tự động cập nhật nếu file cấu hình thay đổi sau đó.
  • IOptionsSnapshot<TOptions>: Đăng ký dạng Scoped. Đọc lại file cấu hình cho mỗi HTTP Request, cho phép reload cấu hình mà không cần restart server. (Không thể inject vào Singleton service).
  • IOptionsMonitor<TOptions>: Đăng ký dạng Singleton. Có cơ chế lắng nghe sự kiện thay đổi file cấu hình (OnChange) theo thời gian thực (Real-time reload), an toàn khi inject vào Singleton hoặc BackgroundService.

Chương 3: C# CLR, Memory Management & Performance Deep-Dive

Câu 11: Phân biệt Value Type và Reference Type trong C#? Chúng được cấp phát ở đâu trên bộ nhớ (Stack vs Heap)?
▼
  • Value Types (struct, enum, int, bool, double): Chứa trực tiếp giá trị dữ liệu. Thường được cấp phát trên Stack (nếu là biến cục bộ trong hàm) hoặc nằm nội tuyến bên trong đối tượng trên Heap (nếu là field của một class). Tự động giải phóng khi rời khỏi scope hàm, không chịu sự quản lý của GC.
  • Reference Types (class, interface, delegate, string, object): Biến chỉ chứa địa chỉ tham chiếu (Pointer) trên Stack, còn đối tượng dữ liệu thực tế được cấp phát trên Heap. Bộ nhớ Heap được quản lý và thu gom tự động bởi Garbage Collector.
Câu 12: Boxing và Unboxing là gì? Tại sao chúng ảnh hưởng tiêu cực đến hiệu năng và cách phòng tránh?
▼
  • Boxing: Quá trình chuyển đổi ngầm định một Value Type thành Reference Type (kiểu object hoặc interface). CLR phải cấp phát một object mới trên Heap và copy giá trị từ Stack sang Heap.
  • Unboxing: Quá trình ép kiểu tường minh từ object trở lại kiểu Value Type gốc, trích xuất giá trị từ Heap về Stack.
  • Tác hại: Gây tốn CPU cho thao tác copy bộ nhớ và sinh ra nhiều rác ngắn hạn trên Heap (Gen 0), làm GC phải chạy liên tục.
  • Cách tránh: Luôn sử dụng Generics (ví dụ List<int> thay vì ArrayList, Dictionary<int, string> thay vì Hashtable).
Câu 13: Phân biệt giữa class, struct và record trong C# hiện đại? Khi nào nên dùng từng loại?
▼
  • class: Reference type trên Heap. Hỗ trợ đầy đủ kế thừa, đa hình, và so sánh theo tham chiếu (Reference Equality - hai biến bằng nhau khi cùng trỏ vào một ô nhớ). Phù hợp cho các Entity nghiệp vụ có vòng đời dài.
  • struct: Value type trên Stack. Không hỗ trợ kế thừa class. Phù hợp cho các đối tượng dữ liệu nhỏ (kích thước < 16 bytes), bất biến, sống ngắn (ví dụ: Point, Coordinate, DateTime).
  • record (C# 9+): Có thể là record class (Reference) hoặc record struct (Value). Tự động hỗ trợ tính bất biến (Immutability với init), so sánh theo giá trị thuộc tính (Value-based Equality), và cú pháp sao chép không phá hủy (with expression). Rất lý tưởng cho DTOs, Commands, Queries, và Events.
Câu 14: Span<T> và Memory<T> trong .NET là gì? Tại sao chúng giúp tối ưu hiệu năng vượt trội?
▼
Span<T> và ReadOnlySpan<T> là các ref struct đại diện cho một vùng nhớ liên tục (có thể nằm trên Stack, Heap, hoặc Unmanaged Memory):
  • Zero-Allocation Slicing: Cho phép cắt nhỏ mảng hoặc chuỗi (ví dụ: parse chuỗi ngày tháng, cắt chuỗi JSON) mà không tạo ra chuỗi mới trên Heap (Zero-Allocation), giúp giảm 90% áp lực lên GC.
  • Memory<T>: Là phiên bản có thể lưu trữ trên Heap và truyền qua các phương thức bất đồng bộ (async/await), vì Span<T> là ref struct nên không thể nằm trong async method state machine.
Câu 15: Tính bất biến của String (String Immutability) và String Interning hoạt động ra sao? Khi nào nên dùng StringBuilder?
▼
  • String Immutability: Chuỗi trong C# là bất biến. Mỗi khi bạn thực hiện phép cộng chuỗi str += "abc", CLR tạo ra một đối tượng String mới trên Heap và bỏ rơi chuỗi cũ.
  • String Interning: CLR duy trì một bảng băm (Intern Pool) chứa các chuỗi ký tự hằng (String literals). Các chuỗi có cùng nội dung sẽ cùng trỏ về một ô nhớ duy nhất trên Heap để tiết kiệm RAM.
  • Khi nào dùng StringBuilder: Khi cần nối chuỗi nhiều lần trong vòng lặp hoặc xử lý văn bản lớn. StringBuilder sử dụng bộ đệm (Buffer) nội bộ có thể thay đổi kích thước mà không cấp phát đối tượng chuỗi mới liên tục.
Câu 16: Phân biệt Delegates, Func, Action và Predicate trong C#?
▼
Tất cả đều là các con trỏ hàm kiểu Type-safe (Type-safe function pointers):
  • Delegate: Khai báo kiểu con trỏ hàm tùy chỉnh do người dùng định nghĩa.
  • Action<T1, T2...>: Delegate dựng sẵn đại diện cho phương thức không trả về giá trị (void), nhận từ 0 đến 16 tham số.
  • Func<T1, T2..., TResult>: Delegate dựng sẵn đại diện cho phương thức có trả về giá trị (TResult là kiểu trả về ở cuối).
  • Predicate<T>: Tương đương với Func<T, bool>, đại diện cho phương thức nhận vào một đối tượng và trả về true/false (thường dùng trong các hàm lọc List.FindAll).

Chương 4: Concurrency, Multithreading & Async/Await

Câu 17: Phân biệt giữa Concurrency (Đồng thời) và Parallelism (Song song)?
▼
  • Concurrency (Đồng thời): Xử lý nhiều công việc trong cùng một khoảng thời gian bằng cách xen kẽ (Context Switching), ngay cả trên 1 nhân CPU (ví dụ: trong lúc chờ I/O database, CPU chuyển sang xử lý HTTP request khác).
  • Parallelism (Song song): Thực thi đồng thời nhiều tác vụ tại cùng một tích tắc trên nhiều lõi CPU vật lý khác nhau (ví dụ: dùng Parallel.ForEach để mã hóa 8 bức ảnh trên 8 nhân CPU).
Câu 18: Các cơ chế đồng bộ luồng (Thread Synchronization) trong C#: lock, Monitor, SemaphoreSlim, Mutex, Interlocked khác nhau như thế nào?
▼
  • lock (object) / Monitor: Khóa độc quyền (Mutual Exclusion) trong cùng một tiến trình (Process). Chỉ cho phép 1 luồng duy nhất được vào khối lệnh tại một thời điểm. (Lưu ý: Không dùng được bên trong async/await).
  • SemaphoreSlim: Cho phép một số lượng luồng xác định (N luồng) truy cập đồng thời vào tài nguyên. Hỗ trợ async/await với phương thức await semaphore.WaitAsync(). Rất lý tưởng cho việc giới hạn số request đồng thời (Throttling).
  • Mutex: Khóa đồng bộ cấp độ Hệ điều hành (OS-level), có thể đồng bộ giữa nhiều tiến trình (Processes) khác nhau trên cùng một máy chủ.
  • Interlocked: Thực hiện các phép toán nguyên tử cấp phần cứng CPU (Atomic operations như tăng biến đếm Interlocked.Increment) với tốc độ nhanh nhất mà không cần khóa luồng.
Câu 19: Khi nào sử dụng Task.WhenAll vs Task.WhenAny vs Parallel.ForEachAsync?
▼
  • Task.WhenAll: Chờ tất cả các Task bất đồng bộ hoàn thành. Phù hợp khi bạn cần gọi 3-4 API độc lập cùng lúc và gom kết quả lại.
  • Task.WhenAny: Hoàn thành ngay khi Task đầu tiên trong danh sách xong. Phù hợp cho bài toán timeout (so sánh Task chính với Task.Delay) hoặc lấy kết quả từ server phản hồi nhanh nhất.
  • Parallel.ForEachAsync (.NET 6+): Duyệt danh sách lớn các phần tử bất đồng bộ và kiểm soát số lượng tác vụ chạy song song tối đa qua MaxDegreeOfParallelism để không làm sập server hoặc nghẽn DB.
Câu 20: System.Threading.Channels trong .NET là gì? Ứng dụng trong mô hình Producer-Consumer ra sao?
▼
System.Threading.Channels là một thư viện hàng đợi (Queue) hiệu năng cao, thread-safe, tối ưu hóa cho mô hình Producer-Consumer bất đồng bộ:
  • Producer: Đẩy dữ liệu vào Channel (writer.WriteAsync(item)) khi nhận request từ Web API.
  • Consumer: Background Worker đọc dữ liệu ra (await foreach (var item in reader.ReadAllAsync())) để xử lý tuần tự hoặc song song.
  • Hỗ trợ Bounded Channel (Hàng đợi có giới hạn dung lượng) giúp chống hiện tượng tràn RAM khi Producer đẩy dữ liệu nhanh hơn tốc độ xử lý của Consumer (Backpressure).

Chương 5: Web API, Middlewares, Filters & Security

Câu 21: Phân biệt sự khác nhau giữa Middleware và Action Filter trong ASP.NET Core?
▼
  • Middleware: Nằm ở tầng ngoài cùng của HTTP Pipeline, xử lý trên đối tượng HttpContext thuần túy trước khi request được chuyển đến Routing và Controller. Không biết thông tin về Action nào sẽ được gọi. Thích hợp cho: Global Logging, CORS, Authentication, Exception Handling.
  • Action Filter: Nằm trong phạm vi của MVC/Routing Pipeline, có quyền truy cập vào ActionExecutingContext (biết rõ Controller nào, Action nào, các tham số DTO và ModelState). Thích hợp cho: Model Validation, Audit log nghiệp vụ, đo thời gian riêng cho từng Action.
Câu 22: Các chiến lược Caching trong Web API: In-Memory Cache, Distributed Cache, và Cache-Aside Pattern?
▼
  • In-Memory Cache (IMemoryCache): Lưu trữ trực tiếp trên RAM của tiến trình web server. Tốc độ nhanh nhất nhưng không chia sẻ được khi scale nhiều server. Cần cấu hình AbsoluteExpiration, SlidingExpiration và SizeLimit để tránh tràn RAM.
  • Distributed Cache (IDistributedCache): Lưu trữ tập trung trên hệ thống ngoài (như Redis/SQL Server), cho phép nhiều web instance cùng chia sẻ chung một kho cache.
  • Cache-Aside Pattern: Ứng dụng kiểm tra dữ liệu trong cache -> Nếu có (Cache Hit), trả về ngay -> Nếu không có (Cache Miss), truy vấn từ Database, ghi kết quả vào Cache với thời gian hết hạn (TTL), rồi trả về client.
Câu 23: Các lỗ hổng bảo mật Web phổ biến (SQL Injection, XSS, CSRF, Broken Auth) được phòng chống như thế nào trong .NET?
▼
  • SQL Injection: Luôn sử dụng Parameterized Queries (EF Core tự động tham số hóa; với Raw SQL thì dùng FromSqlInterpolated hoặc Dapper Parameter). Tuyệt đối không nối chuỗi thô vào câu lệnh SQL.
  • XSS (Cross-Site Scripting): ASP.NET Core tự động mã hóa HTML (HTML Encoding) khi render view. Trong API, cần sanitize và validate dữ liệu đầu vào.
  • CSRF (Cross-Site Request Forgery): Sử dụng [ValidateAntiForgeryToken] cho ứng dụng MVC/Blazor hoặc sử dụng JWT Token lưu trong Header (JWT không tự động gửi như Cookie nên miễn nhiễm với CSRF).
  • CORS: Cấu hình chính xác domain được phép gọi API (WithOrigins) thay vì cho phép tất cả (AllowAnyOrigin) trên production.

Chương 6: Clean Architecture, CQRS & Domain Modeling

Câu 24: Nguyên tắc phụ thuộc (Dependency Rule) trong Clean Architecture được thể hiện bằng code như thế nào?
▼
Tầng Application định nghĩa các Interface trừu tượng (ví dụ IOrderRepository, IEmailService). Tầng Infrastructure tham chiếu đến Application và triển khai (Implement) các interface đó. Tầng API (Web) chỉ đăng ký DI các class từ Infrastructure vào interface của Application mà Controller không cần biết chi tiết bên dưới là SQL Server hay MongoDB.
Câu 25: Pipeline Behaviors trong MediatR là gì và ứng dụng vào Cross-Cutting Concerns ra sao?
▼
IPipelineBehavior<TRequest, TResponse> hoạt động tương tự như Middleware nhưng nằm ở tầng Application cho các Request của MediatR. Cho phép tự động gắn các tính năng:
  • ValidationBehavior: Tự động kích hoạt FluentValidation trước khi Request đến được Handler.
  • LoggingBehavior: Tự động ghi log tên Command/Query và payload.
  • PerformanceBehavior: Cảnh báo khi một Query mất hơn 500ms để thực thi.

Chương 9: Database Optimization & SQL Performance

Câu 26: Chỉ mục Covering Index (INCLUDE) khác gì Composite Index thông thường trong SQL Server?
▼
Trong Composite Index thông thường, tất cả các cột khai báo đều nằm trong cây B-Tree và tham gia vào việc sắp xếp, gây tốn dung lượng cây index và giảm tốc độ INSERT/UPDATE.

Với Covering Index (INCLUDE), chỉ các cột lọc trong WHERE mới nằm ở Key Columns của cây B-Tree. Các cột trong SELECT được đính kèm ở tầng lá (Leaf Node). Khi chạy truy vấn, SQL Server lấy toàn bộ dữ liệu cần thiết ngay trên Index mà không phải tốn thêm thao tác Key Lookup vào bảng chính, giúp tăng tốc độ truy vấn từ 30% đến nhiều lần.
Câu 27: Làm sao để đọc và tối ưu một Execution Plan trong SQL Server (SSMS)?
▼
Mở Execution Plan (Ctrl + M) và tìm các node có Cost % cao nhất từ phải qua trái:
  • Index Seek: Trạng thái tốt nhất (dùng cây B-Tree tìm đúng dòng dữ liệu).
  • Index Scan / Table Scan: Quét toàn bộ bảng/index (cần xem lại điều kiện WHERE hoặc bổ sung index).
  • Key Lookup: Tốn Disk I/O (cần bổ sung Covering Index INCLUDE).
  • Sort / Hash Match: Tốn RAM và CPU TempDB (cần tạo index theo thứ tự ORDER BY hoặc cột JOIN).
