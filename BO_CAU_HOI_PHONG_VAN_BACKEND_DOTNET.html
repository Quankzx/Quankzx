Chương 1: Các Sự Cố Production Kinh Điển (Memory Leak, Race Condition, Deadlock)

Câu 1: Trong môi trường .NET có Garbage Collector (GC), tại sao ứng dụng vẫn bị rò rỉ bộ nhớ (Memory Leak)? Kể tên các nguyên nhân phổ biến nhất?
▼
🎯 Người phỏng vấn muốn kiểm tra: Hiểu biết sâu sắc về GC Root và cách các tham chiếu ngầm làm GC không thể thu hồi bộ nhớ.
GC chỉ thu hồi những đối tượng không còn bất kỳ GC Root nào trỏ tới. Nếu một đối tượng không còn dùng nhưng vẫn bị giữ lại bởi một tham chiếu sống, nó sẽ sống mãi trên Heap gây ra Memory Leak.

5 nguyên nhân kinh điển trong .NET:
  1. Event Handlers không gỡ đăng ký (Unsubscribe): Khi Publisher (sống lâu) đăng ký event với Subscriber (sống ngắn) qua publisher.OnClick += subscriber.Handle, Publisher sẽ giữ một tham chiếu mạnh tới Subscriber -> Subscriber không bao giờ được GC thu hồi. (Khắc phục: Dùng -= trong Dispose() hoặc dùng WeakEventManager).
  2. Static Collections & Singletons: Lưu trữ dữ liệu vào static List<T> hoặc Singleton Service mà không có cơ chế xóa/giới hạn kích thước (Memory Cache không đặt TTL / SizeLimit).
  3. Captive Dependency trong DI: Inject Scoped Service (như DbContext) vào Singleton Service / BackgroundService.
  4. Unmanaged Resources không được giải phóng: Mở FileStream, SqlConnection, HttpClientHandler mà quên gọi Dispose() hoặc không bọc trong khối using.
  5. Timers không dừng (System.Threading.Timer): Timer được GC Root của runtime giữ lại, callback của Timer giữ tham chiếu đến đối tượng chứa nó, khiến đối tượng không thể bị thu dọn.
Câu 2: LOH (Large Object Heap) Fragmentation là gì? Tại sao cấp phát mảng byte lớn liên tục lại nguy hiểm và dùng ArrayPool<T> như thế nào?
▼
🎯 Người phỏng vấn muốn kiểm tra: Kinh nghiệm tối ưu bộ nhớ khi xử lý file lớn/sync dữ liệu hàng trăm MB.
Mọi đối tượng có kích thước từ 85,000 bytes (~83KB) trở lên được CLR đưa trực tiếp vào Large Object Heap (LOH) (thuộc Gen 2).

  • Nguy cơ Phân mảnh (Fragmentation): Mặc định GC không dồn bộ nhớ (Compact) LOH vì chi phí copy các block nhớ lớn rất đắt đỏ. Khi cấp phát và giải phóng các mảng byte lớn liên tục (ví dụ: tải file báo cáo Amazon, xử lý ảnh), LOH sẽ bị "thủng lỗ chỗ". Dù tổng RAM trống còn nhiều, nhưng không có đủ vùng nhớ liên tục cho mảng mới -> Gây OutOfMemoryException.
  • Giải pháp chuẩn - Tái sử dụng bộ đệm bằng ArrayPool<T>: 
    byte[] buffer = ArrayPool<byte>.Shared.Rent(1024 * 128); // Mượn buffer 128KB
try
{
    int bytesRead = await stream.ReadAsync(buffer, 0, buffer.Length);
    // Xử lý dữ liệu...
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer); // Trả lại pool, Zero-Allocation!
}
Câu 3: Khi một Service / Web API trên Production bị tăng RAM liên tục, quy trình điều tra (Troubleshooting) của em là gì?
▼
🎯 Người phỏng vấn muốn kiểm tra: Kỹ năng chẩn đoán sự cố thực tế với các công cụ profiling chuyên nghiệp.
Quy trình 4 bước thực chiến:
  1. Thu thập Dump file mà không làm sập server: Dùng công cụ CLI dotnet-dump collect -p <PID> hoặc dotnet-gcdump để chụp snapshot bộ nhớ tại 2 thời điểm: lúc mới chạy (Base) và lúc RAM tăng cao.
  2. Phân tích Dump: Mở dump file bằng Visual Studio Diagnostic Tools hoặc JetBrains dotMemory / dotnet-dump analyze.
  3. So sánh Snapshot (Diff): Lọc danh sách các Object Type có số lượng instance và dung lượng (Retained Bytes) tăng đột biến giữa 2 mốc thời gian.
  4. Truy vết GC Root: Kiểm tra "Paths to Root" của object đó để xem class hoặc static reference nào đang giữ nó lại, từ đó tìm ra chính xác dòng code gây rò rỉ.
Câu 4: Race Condition là gì? Phân tích bài toán "Trừ tồn kho / Voucher áp dụng 2 lần" khi có 1,000 request đồng thời và giải pháp?
▼
🎯 Người phỏng vấn muốn kiểm tra: Khả năng xử lý tranh chấp dữ liệu đồng thời trong thương mại điện tử / tài chính.
Race Condition xảy ra khi nhiều luồng cùng đọc và ghi vào một dữ liệu chung, và kết quả cuối cùng phụ thuộc vào thứ tự thực thi của các luồng.

Kịch bản lỗi: Sản phẩm còn tồn kho Stock = 1. Request A và Request B đến cùng lúc. Cả 2 cùng đọc DB thấy Stock == 1 hợp lệ, cả 2 cùng thực hiện trừ 1 -> Kết quả Stock = -1 (Bán vượt tồn kho - Overselling).

Các giải pháp xử lý triệt để:
  • 1. Atomic Database Update (Tốt nhất & Nhanh nhất): 
    UPDATE Products 
SET Stock = Stock - 1 
WHERE Id = @productId AND Stock >= 1;
    Nếu RowsAffected == 0 nghĩa là đã hết hàng, trả về thông báo lỗi cho client ngay mà không cần lock.
  • 2. Optimistic Concurrency Control (EF Core): Dùng cột [Timestamp] byte[] RowVersion. Khi update nếu RowVersion bị thay đổi bởi luồng khác, EF Core ném DbUpdateConcurrencyException để ta xử lý retry.
  • 3. Distributed Lock (Redis RedLock / Database Lock): Khóa theo mã VoucherCode + UserId để đảm bảo tại một thời điểm chỉ có 1 request được áp mã giảm giá đó.
Câu 5: Phân biệt Optimistic Concurrency (Khóa lạc quan) và Pessimistic Concurrency (Khóa bi quan)? Khi nào dùng loại nào?
▼
  • Optimistic Concurrency (Khóa lạc quan): Giả định rằng xung đột hiếm khi xảy ra. Không khóa bản ghi lúc đọc dữ liệu. Khi cập nhật (Update), hệ thống kiểm tra xem dữ liệu có bị ai sửa từ lúc đọc đến giờ không (thường dùng Version number / Timestamp). Nếu có xung đột -> Hủy và báo lỗi hoặc Retry.
    Nên dùng: Hệ thống có tỷ lệ Đọc cao, Ghi thấp (Web quản trị, chỉnh sửa thông tin profile). Hiệu năng cao, không gây block DB.
  • Pessimistic Concurrency (Khóa bi quan): Giả định rằng xung đột chắc chắn sẽ xảy ra. Khóa chặt tài nguyên ngay từ thời điểm đọc dữ liệu bằng các khóa độc quyền (ví dụ trong SQL Server: SELECT ... WITH (UPDLOCK, ROWLOCK)). Các transaction khác cố đọc/sửa dòng này đều phải xếp hàng chờ.
    Nên dùng: Khi chi phí xảy ra xung đột quá đắt (Giao dịch ngân hàng, trừ tiền ví, đặt vé xem phim/ghế máy bay lúc Flash Sale).
Câu 6: Phân tích 2 loại Deadlock phổ biến nhất: Deadlock trong C# đa luồng và Deadlock trong SQL Server? Cách phòng tránh?
▼
🎯 Người phỏng vấn muốn kiểm tra: Kỹ năng gỡ rối bế tắc (Deadlock) ở cả tầng Application và Database.
1. Deadlock trong C# (Application-level):
  • Nguyên nhân: Khóa lồng nhau ngược thứ tự. Thread 1 giữ lock(A) và chờ lock(B); cùng lúc đó Thread 2 giữ lock(B) và chờ lock(A) -> Cả 2 luồng bị treo vĩnh viễn.
  • Khắc phục: Luôn luôn lock các đối tượng theo một thứ tự cố định duy nhất trên toàn hệ thống; hoặc sử dụng Monitor.TryEnter(obj, timeout) / SemaphoreSlim.WaitAsync(timeout) có thời gian timeout.
2. Deadlock trong SQL Server (Database-level):
  • Nguyên nhân: Transaction 1 cập nhật Bảng A rồi Bảng B; Transaction 2 cập nhật Bảng B rồi Bảng A. Hoặc do Key Lookup Deadlock (Tx 1 giữ Shared Lock trên Index chờ Exclusive Lock trên bảng chính; Tx 2 làm ngược lại).
  • Khắc phục:
    1. Luôn cập nhật các bảng/dòng theo cùng một thứ tự (sắp xếp theo Primary Key trước khi Update).
    2. Bật RCSI (Read Committed Snapshot Isolation) để việc Đọc không bao giờ block việc Ghi.
    3. Tạo Covering Index (INCLUDE) để triệt tiêu thao tác Key Lookup.
    4. Bắt mã lỗi Deadlock 1205 trong C# và cấu hình Polly Retry tự động thực thi lại sau vài trăm ms.
Câu 7: Thread Pool Starvation và Cache Stampede (Thundering Herd) là gì?
▼
  • Thread Pool Starvation (Nghẽn luồng): Xảy ra khi lập trình viên dùng Sync-over-Async (gọi .Result, .Wait(), hoặc Thread.Sleep()) bên trong các tác vụ bất đồng bộ. Các thread trong Pool bị chiếm dụng và block cứng để chờ I/O. Khi có request mới đến, không còn Worker Thread nào rảnh rỗi. CLR chỉ sinh thêm 1-2 thread/giây (rất chậm), khiến Response Time của toàn bộ website tăng vọt dù CPU đang ở mức rất thấp (< 15%).
  • Cache Stampede (Bão truy vấn khi Cache hết hạn): Xảy ra khi một Cache Key "nóng" (Hot Key có 10,000 req/s) bị hết hạn (Expired). Tại tích tắc đó, cả 10,000 request cùng thấy Cache Miss và cùng lúc gửi truy vấn nặng vào Database -> Database bị quá tải tức thì (Spike CPU 100%) và sập toàn bộ hệ thống.
    Cách chống: Sử dụng khóa SemaphoreSlim in-memory tại thời điểm Cache Miss (chỉ cho 1 luồng duy nhất được query DB và nạp lại Cache, 9,999 luồng còn lại chờ lấy kết quả mới).

Chương 2: 4 Trụ Cột OOP & 5 Nguyên Lý SOLID Thực Tế

Câu 8: Trình bày 4 tính chất cơ bản của lập trình hướng đối tượng (OOP) và cho ví dụ C#?
▼
  • 1. Encapsulation (Đóng gói): Gom nhóm dữ liệu và phương thức vào trong một Class, che giấu trạng thái bên trong qua access modifiers (private, protected) và kiểm soát qua Properties.
  • 2. Abstraction (Trừu tượng hóa): Ẩn chi tiết cài đặt phức tạp, chỉ hiển thị hợp đồng giao tiếp cần thiết qua interface hoặc abstract class (ví dụ: client chỉ gọi IPaymentService.ProcessPayment() mà không cần biết bên dưới gọi Stripe hay PayPal).
  • 3. Inheritance (Kế thừa): Tái sử dụng thuộc tính và phương thức từ class cha (ví dụ: SettlementSyncWorker kế thừa BackgroundService).
  • 4. Polymorphism (Đa hình): Cùng một phương thức nhưng có thể thực thi khác nhau tại runtime (qua override method hoặc triển khai interface).
Câu 9: SOLID là gì? Trình bày chi tiết từng nguyên lý và cách áp dụng trong C#?
▼
  • S - Single Responsibility: Một Class chỉ có một lý do duy nhất để thay đổi (Tách riêng OrderService, InvoiceGenerator, EmailSender).
  • O - Open/Closed: Mở cho mở rộng, đóng cho sửa đổi (Thêm phương thức thanh toán mới bằng cách tạo class mới kế thừa IPaymentMethod thay vì sửa chuỗi switch-case).
  • L - Liskov Substitution: Class con phải thay thế được class cha mà không làm hỏng tính đúng đắn của chương trình (Không throw NotImplementedException ở class con).
  • I - Interface Segregation: Tách Fat Interface thành nhiều interface nhỏ chuyên biệt (IReadOnlyRepository và IWriteRepository).
  • D - Dependency Inversion: Module cấp cao và cấp thấp cùng phụ thuộc vào Interface trừu tượng.
Câu 10: Tại sao nên ưu tiên Composition hơn Inheritance (Favor Composition over Inheritance)?
▼
Kế thừa (Inheritance) tạo ra liên kết chặt chẽ (Tight Coupling) và dễ gặp lỗi Fragile Base Class khi sửa class cha. Trong khi đó, Composition (kết hợp các Interface qua Dependency Injection) giúp hệ thống linh hoạt, dễ dàng thay đổi hành vi tại runtime và dễ viết Unit Test với Mocking.
Câu 11: Phân biệt Abstract Class và Interface trong C#?
▼
  • Interface: Là hợp đồng hành vi (CAN-DO). Một class có thể implement nhiều interface. Không lưu trạng thái (fields), hoàn hảo cho Dependency Injection.
  • Abstract Class: Là danh tính dùng chung (IS-A). Chỉ có thể đơn kế thừa. Có thể chứa fields, constructor, access modifiers và các hàm có sẵn code triển khai.

Chương 3: Inversion of Control (IoC), DI & Design Patterns

Câu 12: Phân biệt Inversion of Control (IoC), Dependency Injection (DI) và Dependency Inversion Principle (DIP)?
▼
DIP là Nguyên lý thiết kế (SOLID). IoC là Mô hình kiến trúc đảo ngược quyền điều khiển luồng thực thi cho Framework. DI là Mẫu thiết kế (Design Pattern) cụ thể để hiện thực hóa IoC và DIP bằng cách "tiêm" phụ thuộc từ bên ngoài vào class qua constructor.
Câu 13: Service Locator Pattern là gì và tại sao nó bị coi là một Anti-Pattern?
▼
Service Locator dùng IServiceProvider.GetService<T>() trực tiếp bên trong method. Nó bị coi là Anti-Pattern vì che giấu sự phụ thuộc của class (Hidden Dependencies), gây khó khăn khi viết Unit Test và dễ gây lỗi crash tại runtime nếu quên đăng ký service trong container.
Câu 14: Triển khai Thread-Safe Singleton chuẩn nhất trong C# với System.Lazy<T>?
▼ 
public sealed class SingletonService
{
    private static readonly Lazy<SingletonService> _instance =
        new Lazy<SingletonService>(() => new SingletonService(), LazyThreadSafetyMode.ExecutionAndPublication);

    private SingletonService() { }

    public static SingletonService Instance => _instance.Value;
}
Đảm bảo 100% an toàn đa luồng và chỉ khởi tạo khi được truy cập lần đầu tiên.
Câu 15: Strategy Pattern và ứng dụng thay thế chuỗi if-else / switch-case phức tạp?
▼
Đóng gói từng thuật toán/nghiệp vụ vào class riêng biệt triển khai chung một interface (ví dụ IShippingCalculator). Tại runtime, hệ thống lấy đúng Strategy từ DI Container hoặc Dictionary theo loại đơn hàng, giúp code tuân thủ Open/Closed Principle.
Câu 16: Options Pattern trong .NET: Phân biệt IOptions, IOptionsSnapshot và IOptionsMonitor?
▼
  • IOptions<T>: Singleton, đọc cấu hình 1 lần duy nhất lúc start app.
  • IOptionsSnapshot<T>: Scoped, đọc lại cấu hình cho mỗi HTTP Request.
  • IOptionsMonitor<T>: Singleton, tự động lắng nghe sự kiện thay đổi file appsettings.json theo thời gian thực (Real-time reload).

Chương 4: C# CLR, Memory Management & Performance Deep-Dive

Câu 17: Phân biệt Value Type vs Reference Type (Stack vs Heap) và Boxing/Unboxing?
▼
Value Type (struct, int, bool) lưu giá trị trực tiếp trên Stack, giải phóng khi rời scope. Reference Type (class, string, object) lưu con trỏ trên Stack và dữ liệu thực tế trên Heap (do GC quản lý). Boxing ép Value Type sang Reference Type (tạo object trên Heap); Unboxing trích xuất ngược lại. Tránh bằng cách dùng Generics.
Câu 18: So sánh class vs struct vs record trong C# hiện đại?
▼
  • class: Reference Type, hỗ trợ kế thừa, so sánh theo địa chỉ ô nhớ.
  • struct: Value Type, lưu trên Stack, phù hợp cho object nhỏ < 16 bytes, sống ngắn.
  • record: Tự động hỗ trợ tính bất biến (Immutability), so sánh theo giá trị thuộc tính (Value Equality), rất lý tưởng cho DTOs, Commands, Queries.
Câu 19: Span<T> và Memory<T> là gì và cơ chế Zero-Allocation?
▼
Span<T> là ref struct đại diện cho một vùng nhớ liên tục. Cho phép cắt nhỏ chuỗi hoặc mảng (Slicing) mà không tạo đối tượng mới trên Heap (Zero-Allocation). Memory<T> là phiên bản lưu được trên Heap để dùng trong các phương thức async/await.
Câu 20: String Immutability, String Interning và khi nào nên dùng StringBuilder?
▼
Chuỗi trong C# là bất biến. Mỗi phép cộng chuỗi += tạo một đối tượng String mới trên Heap. CLR duy trì bảng String Interning để gom các chuỗi hằng trùng nhau vào cùng 1 ô nhớ. Khi cần nối chuỗi nhiều lần trong vòng lặp, luôn dùng StringBuilder để tránh cấp phát bộ nhớ liên tục.

Chương 10: Cơ Sở Dữ Liệu SQL Server & Tối Ưu Hóa Truy Vấn

Câu 21: Phân biệt Clustered Index vs Non-Clustered Index và Covering Index (INCLUDE)?
▼
  • Clustered Index: Sắp xếp dữ liệu vật lý trên ổ đĩa. Mỗi bảng chỉ có 1 Clustered Index.
  • Non-Clustered Index: Cây B-Tree riêng biệt trỏ về bảng chính.
  • Covering Index (INCLUDE): Đính kèm các cột cần SELECT vào tầng lá của Index, giúp SQL Server lấy dữ liệu ngay trên Index mà không cần Key Lookup vào bảng chính, tăng tốc độ truy vấn từ 30% đến nhiều lần.
Câu 22: Lỗi N+1 Query trong EF Core là gì và 3 cách khắc phục triệt để?
▼
Xảy ra khi load danh sách cha (1 query) rồi lặp qua từng phần tử để truy cập con, sinh thêm N query nữa -> Tổng cộng 1 + N queries.
Khắc phục:
  1. Projection (Tốt nhất): Dùng .Select() chỉ định rõ DTO để EF Core tự sinh SQL JOIN tối ưu.
  2. Eager Loading: Dùng .Include() và .ThenInclude().
  3. Split Query: Dùng .AsSplitQuery() khi có nhiều Include phức tạp để tránh Cartesian Explosion.
Câu 23: Tại sao luôn nên dùng .AsNoTracking() cho các truy vấn Read-Only trong EF Core?
▼
.AsNoTracking() bỏ qua việc đưa entity vào Change Tracker, giúp tiết kiệm dung lượng RAM và tăng tốc độ đọc từ 20-30%. Rất cần thiết cho API GET, báo cáo và các Worker chạy ngầm.
