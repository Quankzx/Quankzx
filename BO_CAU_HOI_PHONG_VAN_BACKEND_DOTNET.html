Chương 1: C# & .NET Core Core Concepts (Nền tảng)

Câu 1: Trong .NET, cơ chế Dependency Injection (DI) hỗ trợ các loại Service Lifetime nào? Khi nào sử dụng từng loại?
▼
🎯 Người phỏng vấn muốn kiểm tra: Hiểu biết về quản lý vòng đời bộ nhớ và các lỗi cấp phát tài nguyên trong .NET.
Trong .NET có 3 loại Lifetime chính:
  • Transient (AddTransient): Tạo một instance mới mỗi lần được yêu cầu (resolve). Phù hợp cho các service nhẹ, không lưu trạng thái (Stateless) như Helpers, Mappers, Validators.
  • Scoped (AddScoped): Tạo một instance duy nhất trong phạm vi của một Request (trong Web API là một HTTP Request). Phù hợp cho các service gắn liền với ngữ cảnh request như DbContext, Repositories, Current User Context.
  • Singleton (AddSingleton): Tạo duy nhất một instance cho toàn bộ vòng đời của ứng dụng. Phù hợp cho các service dùng chung như Caching in-memory, Configuration, hoặc các tiến trình chạy nền (BackgroundService).
Câu 2: Lỗi "Captive Dependency" trong Dependency Injection là gì và làm sao để khắc phục?
▼
🎯 Người phỏng vấn muốn kiểm tra: Kinh nghiệm xử lý lỗi bất đồng bộ vòng đời giữa Scoped và Singleton.
Captive Dependency xảy ra khi một service có vòng đời dài (ví dụ: Singleton) phụ thuộc và inject trực tiếp một service có vòng đời ngắn hơn (ví dụ: Scoped DbContext) qua constructor. Khi đó, service Scoped sẽ bị giữ lại (bắt giữ) và sống mãi mãi theo Singleton.

Hậu quả: DbContext không bao giờ được giải phóng, gây rò rỉ bộ nhớ (Memory Leak) và lỗi đa luồng (Concurrency Exceptions) khi nhiều luồng cùng gọi vào một DbContext instance.
Cách khắc phục: Trong Singleton (như BackgroundService), ta inject IServiceScopeFactory. Mỗi khi cần dùng Scoped service, ta tạo scope thủ công bằng using (var scope = _scopeFactory.CreateScope()) và resolve service từ scope đó.
Câu 3: Lập trình bất đồng bộ (async/await) trong C# hoạt động như thế nào? Tại sao nên tránh dùng .Result hoặc .Wait()?
▼
🎯 Người phỏng vấn muốn kiểm tra: Khả năng tối ưu I/O Bound, Thread Pool và phòng tránh Deadlock.
  • async/await không tạo ra Thread mới cho các tác vụ I/O (gọi API, truy vấn DB, đọc file). Khi gặp từ khóa await, luồng hiện tại được trả về Thread Pool để phục vụ request khác. Khi tác vụ I/O hoàn thành, một luồng từ Pool sẽ được cấp phát để tiếp tục thực thi đoạn code sau await.
  • Tại sao tránh .Result / .Wait(): Đây là kỹ thuật Sync-over-Async làm block luồng hiện tại để chờ Task hoàn thành. Điều này dễ dẫn đến Deadlock và làm cạn kiệt tài nguyên Thread Pool (Thread Pool Starvation), khiến ứng dụng không thể xử lý thêm request mới.
  • Nguyên tắc vàng: Luôn áp dụng "Async all the way" từ Controller xuống tầng Database/Network.
Câu 4: Middleware trong ASP.NET Core là gì? Em thường dùng Middleware để xử lý những việc gì?
▼
🎯 Người phỏng vấn muốn kiểm tra: Kiến thức về HTTP Request Pipeline trong ASP.NET Core.
Middleware là các khối code được ghép nối với nhau thành một đường ống (Pipeline) để xử lý các HTTP Request và Response theo mô hình Chain of Responsibility.

Các ứng dụng thực tế em thường triển khai:
  • Global Exception Handling: Bắt tất cả các lỗi unhandled exception trong hệ thống, ghi log chi tiết và trả về response chuẩn RFC 7807 (Problem Details) với mã HTTP 500.
  • Authentication & Authorization: Kiểm tra JWT Bearer token và xác thực quyền người dùng.
  • Request/Response Logging & Timing: Đo thời gian thực thi (Elapsed time) của API để phát hiện các endpoint bị chậm.
Câu 5: Quá trình Garbage Collection (GC) trong .NET hoạt động như thế nào và làm sao để giải phóng unmanaged resources?
▼
🎯 Người phỏng vấn muốn kiểm tra: Khả năng quản lý bộ nhớ và tối ưu ứng dụng lâu dài.
  • GC trong .NET tự động thu hồi bộ nhớ trên Heap theo cơ chế 3 thế hệ (Generational GC): Gen 0 (đối tượng mới tạo, ngắn hạn), Gen 1 (vùng đệm), và Gen 2 (đối tượng sống lâu dài như Static/Singleton). Các đối tượng lớn hơn 85,000 bytes được đưa vào LOH (Large Object Heap).
  • Giải phóng tài nguyên Unmanaged (File stream, DB connection, Socket): Cần triển khai pattern IDisposable / IAsyncDisposable. Trong code sử dụng, luôn bọc trong khối using (var resource = ...) hoặc using var ... để đảm bảo phương thức Dispose() luôn được gọi tự động ngay cả khi có Exception xảy ra.
Câu 6: Phân biệt giữa IEnumerable, IQueryable và IList trong C#?
▼
🎯 Người phỏng vấn muốn kiểm tra: Tránh lỗi lọc dữ liệu trên RAM (In-Memory filtering) gây sập server.
  • IQueryable<T>: Hoạt động dựa trên Expression Tree. Khi ta viết .Where() hay .Select(), điều kiện được dịch thành câu lệnh SQL và thực thi trực tiếp trên Database server.
  • IEnumerable<T>: Dùng để duyệt dữ liệu tuần tự. Nếu gọi .Where() trên IEnumerable, toàn bộ dữ liệu từ DB đã được tải về RAM của server rồi mới lọc (In-Memory filtering) -> gây chậm và tốn bộ nhớ nếu bảng lớn.
  • IList<T> / List<T>: Tập hợp dữ liệu đã nằm hoàn toàn trong bộ nhớ RAM, hỗ trợ thêm/sửa/xóa và truy xuất theo chỉ mục [index].

Chương 2: Web API & Clean Architecture (Thiết kế hệ thống)

Câu 7: Em hiểu thế nào về kiến trúc Clean Architecture và tại sao nên áp dụng nó cho dự án Backend?
▼
🎯 Người phỏng vấn muốn kiểm tra: Tư duy phân tầng kiến trúc và quản lý sự phụ thuộc.
Clean Architecture chia hệ thống thành các tầng độc lập theo nguyên tắc Dependency Rule (Phụ thuộc hướng vào trong):
  • Domain (Lõi): Chứa Entities, Enums, Value Objects. Hoàn toàn không phụ thuộc vào bất kỳ framework hoặc thư viện ngoài nào.
  • Application: Chứa Business Logic, Use Cases, CQRS Handlers, DTOs, Validation. Chỉ phụ thuộc vào Domain.
  • Infrastructure: Triển khai kết nối CSDL (EF Core DbContext), Gọi API bên ngoài, Lưu trữ file (AWS S3), JWT Authentication.
  • Presentation / API: Controllers, Middlewares, Background Workers.
Lợi ích: Dễ viết Unit Test (mock dependencies dễ dàng), dễ thay thế công nghệ (ví dụ đổi SQL Server sang PostgreSQL mà không cần sửa Business Logic ở tầng Application).
Câu 8: Mô hình CQRS (Command Query Responsibility Segregation) là gì? Khi nào nên áp dụng?
▼
🎯 Người phỏng vấn muốn kiểm tra: Khả năng tách biệt luồng Đọc và Ghi để tối ưu hệ thống.
CQRS là mô hình tách biệt rõ ràng giữa hai luồng xử lý:
  • Commands (Ghi): Các hành động thay đổi trạng thái dữ liệu (Create, Update, Delete). Cần validate chặt chẽ, kiểm tra tính toàn vẹn nghiệp vụ.
  • Queries (Đọc): Các hành động chỉ lấy dữ liệu để hiển thị (Read-only). Cần tối ưu tốc độ đọc tối đa, có thể bypass tầng nghiệp vụ phức tạp, dùng .AsNoTracking() hoặc Dapper.
Trong .NET, em thường kết hợp CQRS với thư viện MediatR để mỗi use-case là một class Request và Handler riêng biệt, giúp code gọn gàng, tránh việc một Service class bị phình to hàng nghìn dòng.
Câu 9: Cơ chế xác thực và phân quyền bằng JWT Token trong Web API hoạt động như thế nào?
▼
🎯 Người phỏng vấn muốn kiểm tra: Kỹ năng bảo mật API Backend.
  • Authentication (Xác thực): Người dùng gửi thông tin đăng nhập. Nếu hợp lệ, backend tạo ra một chuỗi Access Token (JWT) chứa các Claims (UserId, Email, Roles) được ký bằng Secret Key đối xứng (HMAC-SHA256). Client đính kèm token này vào header Authorization: Bearer <token> cho các request tiếp theo.
  • Authorization (Phân quyền): Backend sử dụng attribute [Authorize(Roles = "Admin,Manager")] hoặc Policy-based Authorization để kiểm tra quyền hạn trước khi cho phép request đi vào Action.
  • Refresh Token: Access Token có hạn ngắn (ví dụ 15-30 phút). Khi hết hạn, client gửi Refresh Token (lưu an toàn trong DB) lên để xin cấp mới Access Token mà người dùng không cần đăng nhập lại.
Câu 10: Tại sao nên dùng FluentValidation thay vì gắn DataAnnotations trực tiếp lên Model/DTO?
▼
🎯 Người phỏng vấn muốn kiểm tra: Tư duy Clean Code và nguyên lý Single Responsibility.
  • DataAnnotations: Gắn các attribute [Required], [MaxLength] trực tiếp lên DTO. Nhược điểm: làm bẩn class DTO, khó viết các logic validate phức tạp (ví dụ validate phụ thuộc nhiều trường, kiểm tra điều kiện nghiệp vụ hoặc truy vấn DB bất đồng bộ).
  • FluentValidation: Tách toàn bộ logic kiểm tra sang một class riêng kế thừa AbstractValidator<T>. Hỗ trợ validate có điều kiện (When(), Unless()), quy tắc bất đồng bộ (MustAsync()), và dễ dàng viết Unit Test độc lập cho các rule kiểm tra.
Câu 11: Em thiết kế chuẩn RESTful Web API như thế nào? (HTTP Methods, Status Codes, URL Naming)
▼
🎯 Người phỏng vấn muốn kiểm tra: Tiêu chuẩn thiết kế API chuyên nghiệp.
  • URL Naming: Sử dụng danh từ số nhiều đại diện cho tài nguyên (Resource), ví dụ: /api/orders, /api/orders/{id}/items.
  • HTTP Methods:
    • GET: Lấy dữ liệu (Idempotent, Safe).
    • POST: Tạo mới tài nguyên.
    • PUT: Cập nhật toàn bộ tài nguyên (Idempotent).
    • PATCH: Cập nhật một phần thuộc tính tài nguyên.
    • DELETE: Xóa tài nguyên (Idempotent).
  • HTTP Status Codes chuẩn: 200 OK, 201 Created (kèm header Location), 204 No Content, 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 429 Too Many Requests, 500 Internal Server Error.
Câu 12: Hệ thống Multi-Tenancy (phục vụ nhiều công ty/khách hàng trên cùng 1 hệ thống) được thiết kế và cách ly dữ liệu ra sao?
▼
🎯 Người phỏng vấn muốn kiểm tra: Kiến trúc SaaS và bảo mật dữ liệu giữa các doanh nghiệp.
Cách tiếp cận phổ biến và hiệu quả nhất là Shared Database, Shared Schema (Row-level Isolation):
  • Mọi bảng dữ liệu nghiệp vụ đều có thêm cột TenantId.
  • Khi có request đến, Middleware trích xuất TenantId từ JWT Token hoặc Subdomain và lưu vào ICurrentTenantService.
  • Trong EF Core DbContext, ta sử dụng tính năng Global Query Filter: 
    modelBuilder.Entity<Order>().HasQueryFilter(e => e.TenantId == _currentTenant.TenantId);
  • EF Core sẽ tự động thêm điều kiện WHERE TenantId = @tenantId vào mọi câu truy vấn, loại bỏ hoàn toàn nguy cơ rò rỉ dữ liệu giữa các khách hàng.

Chương 3: Background Worker Services & Data Synchronization

Câu 13: Em thường sử dụng Background Worker Service trong các dự án cho những mục đích gì?
▼
🎯 Người phỏng vấn muốn kiểm tra: Trải nghiệm thực tế với các tác vụ chạy ngầm.
Em sử dụng BackgroundService kế thừa từ IHostedService cho các tác vụ nền:
  • Đồng bộ dữ liệu định kỳ: Tự động gọi API bên thứ ba (như sàn TMĐT Amazon, đối tác vận chuyển) để kéo đơn hàng mới, cập nhật tồn kho, đối soát giao dịch tài chính.
  • Xử lý tác vụ nặng bất đồng bộ: Xử lý các file báo cáo lớn, tạo file export Excel/PDF, gửi email thông báo hàng loạt mà không bắt người dùng trên Web phải chờ đợi.
  • Dọn dẹp và bảo trì hệ thống: Xóa các file tạm, dọn dẹp các session hết hạn, kiểm tra tính toàn vẹn của dữ liệu định kỳ.
Câu 14: Khi máy chủ restart hoặc ứng dụng bị shutdown, làm sao để Worker dừng một cách an toàn (Graceful Shutdown)?
▼
  • Phương thức ExecuteAsync(CancellationToken stoppingToken) nhận vào một stoppingToken. Khi ứng dụng nhận tín hiệu dừng (SIGTERM/Stop Service), token này được kích hoạt trạng thái hủy (Cancelled).
  • Cách xử lý:
    1. Luôn kiểm tra !stoppingToken.IsCancellationRequested trong các vòng lặp và truyền token vào các hàm I/O async (HttpClient.GetAsync, DbContext.SaveChangesAsync, Task.Delay).
    2. Chia nhỏ công việc thành từng Batch/Chunk nhỏ (ví dụ 50-100 items). Sau mỗi chunk, commit Transaction và lưu mốc trạng thái LastSyncedAt vào DB.
    3. Nếu bị ngắt giữa chừng, Worker hủy chunk hiện tại an toàn. Lần khởi động tiếp theo sẽ đọc mốc LastSyncedAt gần nhất để chạy tiếp mà không bị trùng lặp hay mất dữ liệu.
Câu 15: Làm sao đảm bảo tính Idempotency (không bị ghi trùng lặp dữ liệu) khi Worker đồng bộ dữ liệu nhiều lần?
▼
🎯 Người phỏng vấn muốn kiểm tra: Tư duy bảo đảm tính toàn vẹn dữ liệu (Data Integrity).
Khi gọi API bên ngoài, Worker có thể gặp sự cố mất mạng sau khi đã nhận dữ liệu nhưng chưa kịp lưu, dẫn đến việc lần chạy sau sẽ lấy lại dữ liệu đó.

Giải pháp:
  • Tạo Unique Index / Unique Constraint trên Database cho các mã định danh nghiệp vụ duy nhất (ví dụ: ExternalOrderId, TransactionId, SKU).
  • Áp dụng chiến lược Upsert: Kiểm tra nếu bản ghi đã tồn tại theo mã định danh duy nhất thì chỉ thực hiện Update trạng thái, nếu chưa có thì mới Insert mới.
  • Bọc toàn bộ thao tác ghi của một batch vào trong Database Transaction.
Câu 16: Làm sao xử lý việc đọc và xử lý các file dữ liệu rất lớn (hàng trăm MB) trong Worker mà không làm tràn bộ nhớ RAM (OutOfMemoryException)?
▼
  • Tránh: Không bao giờ đọc toàn bộ file vào chuỗi String hoặc Byte Array trên RAM (ReadAllText, ReadAllBytes).
  • Giải pháp chuẩn:
    • Sử dụng Streaming I/O: Đọc dữ liệu dạng luồng thông qua StreamReader kết hợp các thư viện streaming parser (như CsvHelper hoặc JSON Stream Parser).
    • Đọc và xử lý từng dòng một (Line-by-line processing).
    • Gom dữ liệu theo từng batch nhỏ (ví dụ 500-1000 dòng), ghi vào Database bằng EF Core rồi gọi ChangeTracker.Clear() để giải phóng bộ nhớ của ORM ngay lập tức.
Câu 17: Khi có nhiều Background Worker cùng chạy, làm sao tránh xung đột tài nguyên hoặc làm cạn kiệt Connection Pool của Database?
▼
  • Thời gian khởi chạy so le (Staggered Schedules): Không cho các worker chạy cùng một tích tắc lúc hệ thống khởi động.
  • Mở kết nối ngắn nhất có thể: Chỉ tạo scope và mở kết nối DB khi thực sự bắt đầu ghi/đọc dữ liệu, giải phóng (Dispose) ngay sau khi batch hoàn thành, không giữ DbContext mở trong lúc đang gọi API bên ngoài tốn thời gian.
  • Điều tiết đồng thời (Concurrency Throttling): Sử dụng SemaphoreSlim để giới hạn số lượng tác vụ được phép truy cập tài nguyên nặng cùng một lúc.
Câu 18: Cơ chế tự động làm mới (Token Rotation) khi làm việc với các API bên thứ ba sử dụng OAuth2 Access Token diễn ra như thế nào?
▼
Access Token của các bên thứ ba (như Amazon LWA) thường chỉ có hạn sử dụng ngắn (1 giờ):
  • Xây dựng một TokenProvider quản lý Access Token trong In-Memory Cache.
  • Trước khi thực hiện bất kỳ cuộc gọi API nào, hệ thống kiểm tra token trong cache. Nếu token còn hạn (trừ đi khoảng an toàn 5 phút), trả về dùng ngay.
  • Nếu token sắp hết hạn hoặc đã hết, sử dụng Refresh Token gửi request cấp phát lại token mới, cập nhật vào cache và tiếp tục cuộc gọi API. Sử dụng SemaphoreSlim để khóa luồng, tránh việc nhiều worker cùng lúc gọi refresh token (Cache Stampede).

Chương 4: API Resilience, Rate Limiting & Polly

Câu 19: Khi tích hợp với API bên thứ ba gặp mã lỗi 429 Too Many Requests (Rate Limiting), em xử lý như thế nào?
▼
Các hệ thống lớn thường áp dụng thuật toán **Token Bucket** hoặc **Leaky Bucket** để giới hạn request.

Cách xử lý chuyên nghiệp:
  • Cấp độ Request (Transient Fault Handling): Sử dụng thư viện **Polly** thiết lập chính sách **Retry với Exponential Backoff kèm Jitter** (thử lại sau 2s, 4s, 8s... cộng thêm độ lệch ngẫu nhiên vài trăm ms).
  • Cấp độ Quản lý hàng đợi (Batch Throttling): Nếu quota bị chạm trần liên tục, worker chuyển sang trạng thái tạm nghỉ (Delay) một khoảng thời gian dài hơn (ví dụ vài giờ đối với các báo cáo nặng) trước khi thử lại chunk tiếp theo để tránh bị đối tác khóa tài khoản.
Câu 20: Em hiểu thế nào về Circuit Breaker Pattern và các trạng thái của nó?
▼
Circuit Breaker là mẫu thiết kế giúp bảo vệ hệ thống không bị treo khi dịch vụ đích gặp sự cố nghiêm trọng, hoạt động qua 3 trạng thái:
  • Closed (Đóng): Trạng thái bình thường, mọi request đều đi qua. Hệ thống theo dõi tỷ lệ lỗi.
  • Open (Ngắt mạch): Khi tỷ lệ lỗi vượt ngưỡng cho phép (ví dụ >50% lỗi trong 30s), mạch ngắt ngay lập tức. Tất cả các request tiếp theo bị từ chối tức thì (Fast Fail) mà không gửi ra mạng, giúp dịch vụ đích có thời gian phục hồi và không làm nghẽn thread của bên gọi.
  • Half-Open (Nửa mở): Sau một khoảng thời gian chờ (Cooldown), mạch cho phép một số lượng nhỏ request đi qua thử nghiệm. Nếu thành công, mạch đóng lại (Closed); nếu thất bại, tiếp tục ngắt (Open).
Câu 21: Tại sao trong Retry Policy của Polly luôn cần bổ sung "Jitter" (Độ lệch ngẫu nhiên)?
▼
Để giải quyết bài toán Thundering Herd Problem (Hiện tượng bầy đàn).
Nếu không có Jitter, khi một dịch vụ gặp sự cố, tất cả 100 client bị lỗi tại cùng 1 giây sẽ cùng đợi đúng 2s, 4s, 8s để thử lại. Điều này tạo ra các đợt "sóng thần" request đồng loạt ập vào server đích tại cùng một tích tắc, khiến server càng bị quá tải và không thể gượng dậy.
Jitter thêm một khoảng thời gian ngẫu nhiên (ví dụ 2s + Random(100ms - 500ms)), giúp phân tán đều các lượt thử lại trên dòng thời gian.
Câu 22: Khi gọi API bên thứ ba bị Timeout hoặc Network Drop mà không rõ bên kia đã xử lý hay chưa, em làm thế nào?
▼
  • Đối với tác vụ GET (Đọc): Có thể an toàn thử lại vì tính chất Idempotent.
  • Đối với tác vụ POST (Tạo đơn / Thanh toán / Ghi dữ liệu):
    1. Sử dụng Idempotency Key (Header) truyền kèm request nếu bên thứ ba hỗ trợ.
    2. Trước khi quyết định gọi lại, thực hiện một truy vấn (Query Status / GET) dựa trên mã tham chiếu nghiệp vụ duy nhất để xác nhận xem phía đối tác đã tạo thành công hay chưa.
Câu 23: Em sử dụng HttpClientFactory và Typed Client trong .NET như thế nào để tránh lỗi Socket Exhaustion?
▼
  • Nếu khởi tạo new HttpClient() thủ công liên tục, khi dispose socket vẫn bị kẹt ở trạng thái TIME_WAIT của hệ điều hành, dẫn đến lỗi Socket Exhaustion khi tải cao.
  • Giải pháp chuẩn: Sử dụng IHttpClientFactory đăng ký Typed Client trong Program.cs: 
    services.AddHttpClient<IExternalApiClient, ExternalApiClient>(client => {
    client.BaseAddress = new Uri("https://api.example.com/");
    client.Timeout = TimeSpan.FromSeconds(30);
}).AddPolicyHandler(GetRetryPolicy());
  • HttpClientFactory tự động quản lý vòng đời của HttpMessageHandler, tái sử dụng các kết nối socket bên dưới một cách tối ưu.

Chương 5: Database Optimization & SQL Performance

Câu 24: Phân biệt Clustered Index và Non-Clustered Index trong cơ sở dữ liệu quan hệ?
▼
  • Clustered Index: Quyết định trực tiếp thứ tự sắp xếp vật lý của dữ liệu trên đĩa cứng (Leaf node chính là Data page chứa toàn bộ dữ liệu dòng). Mỗi bảng chỉ có duy nhất 1 Clustered Index (thường mặc định là Primary Key).
  • Non-Clustered Index: Là một cấu trúc cây B-Tree độc lập tách rời bảng dữ liệu. Leaf node chỉ chứa các cột được đánh index kèm theo một con trỏ (Row Pointer / Clustered Key) trỏ về dòng dữ liệu thực tế trên bảng chính. Một bảng có thể tạo nhiều Non-Clustered Index.
Câu 25: Covering Index với mệnh đề INCLUDE trong SQL Server hoạt động như thế nào và đem lại lợi ích gì?
▼
  • Vấn đề: Khi Non-Clustered Index chỉ chứa các cột trong điều kiện WHERE, nhưng câu lệnh SELECT lại cần lấy thêm các cột khác, SQL Server buộc phải thực hiện thêm thao tác Key Lookup / RID Lookup vào bảng chính để lấy dữ liệu -> gây tốn nhiều Disk I/O.
  • Giải pháp với INCLUDE: 
    CREATE NONCLUSTERED INDEX IX_Orders_Status_Date
ON Orders (OrderStatus, OrderDate)
INCLUDE (TotalAmount, CustomerName, TrackingCode);
  • Các cột trong INCLUDE được đính kèm ở tầng lá (Leaf Node) của Index mà không làm phình cây B-Tree. Khi truy vấn, SQL Server lấy được toàn bộ dữ liệu ngay trên Index mà không cần Key Lookup, giúp tăng tốc độ truy vấn từ 30% đến nhiều lần.
Câu 26: Vấn đề N+1 Query trong ORM là gì? Em xử lý nó ra sao trong Entity Framework Core?
▼
  • Vấn đề: Xảy ra khi ta truy vấn danh sách N bản ghi cha (1 query), sau đó lặp qua từng phần tử để truy cập navigation property con, ORM sẽ tự động bắn thêm N câu query riêng lẻ nữa vào DB -> Tổng cộng 1 + N queries, gây nghẽn kết nối DB nghiêm trọng.
  • Cách khắc phục:
    1. Projection (Tốt nhất): Dùng .Select() để chỉ định đúng các trường DTO cần lấy, EF Core sẽ tự động sinh câu query SQL JOIN tối ưu nhất.
    2. Eager Loading: Sử dụng .Include() và .ThenInclude() để JOIN sẵn dữ liệu con ngay từ câu query đầu tiên.
    3. Split Query: Dùng .AsSplitQuery() khi có nhiều Include phức tạp để tránh việc nhân bản dữ liệu (Cartesian Explosion).
Câu 27: .AsNoTracking() trong EF Core hoạt động như thế nào và khi nào nên dùng?
▼
  • Mặc định, EF Core đưa mọi entity query được vào Change Tracker để theo dõi sự thay đổi phục vụ việc gọi SaveChangesAsync(). Quá trình này tốn bộ nhớ RAM và CPU.
  • Khi gọi .AsNoTracking(), EF Core trả về các đối tượng POCO thuần túy mà không đưa vào Change Tracker.
  • Nên dùng: Cho tất cả các truy vấn chỉ đọc (Read-only queries, API GET, báo cáo, export file), giúp tăng tốc độ thực thi và tiết kiệm đáng kể dung lượng bộ nhớ.
Câu 28: Deadlock trong cơ sở dữ liệu là gì? Làm sao để phòng tránh khi cập nhật đồng thời nhiều dòng?
▼
Deadlock xảy ra khi hai hay nhiều transaction giữ khóa (Lock) trên tài nguyên mà bên kia cần, và chờ đợi lẫn nhau vô thời hạn.

Cách phòng ngừa:
  • Truy cập tài nguyên theo cùng một thứ tự: Luôn cập nhật các bảng/dòng theo cùng một trình tự logic (ví dụ sắp xếp theo Primary Key tăng dần trước khi update hàng loạt).
  • Giữ Transaction ngắn nhất có thể: Không đặt các lời gọi API bên ngoài hoặc tính toán nặng bên trong khối Transaction DB.
  • Sử dụng Snapshot Isolation (RCSI): Bật READ_COMMITTED_SNAPSHOT để việc Đọc không bao giờ block việc Ghi và việc Ghi không block Đọc.
  • Đánh Index đầy đủ: Tránh việc câu lệnh UPDATE bị Table Scan gây khóa toàn bộ bảng.
Câu 29: Phương thức ExecuteUpdateAsync / ExecuteDeleteAsync trong EF Core 7/8 có gì vượt trội so với cách cập nhật truyền thống?
▼
  • Cách truyền thống: Phải load toàn bộ entity về RAM -> sửa thuộc tính -> gọi SaveChangesAsync(). Nếu update 10,000 dòng, EF Core phải load 10,000 entity vào RAM và sinh 10,000 câu lệnh UPDATE riêng biệt.
  • ExecuteUpdateAsync / ExecuteDeleteAsync: Thực thi trực tiếp câu lệnh UPDATE / DELETE trên Database server bằng 1 câu query duy nhất mà không cần tải dữ liệu về RAM và không qua Change Tracker, mang lại hiệu năng cao gấp hàng chục lần cho các tác vụ cập nhật hàng loạt.
Câu 30: Khi nào em lựa chọn Entity Framework Core và khi nào nên dùng Dapper / Raw SQL?
▼
Em thường áp dụng mô hình Hybrid (Kết hợp cả hai):
  • Dùng EF Core: Cho các nghiệp vụ CRUD chuẩn, quản lý Domain Entities, tận dụng tính năng Unit of Work (DbContext), Validation, và quản lý Database Migrations an toàn.
  • Dùng Dapper / Raw SQL: Cho các câu query báo cáo tổng hợp phức tạp (Reporting), dashboard thống kê cần JOIN nhiều bảng, hoặc các tác vụ Bulk Insert/Update hàng chục nghìn dòng cần tốc độ tối đa.

Chương 6: System Monitoring & Watchdog Services

Câu 31: Hệ thống Watchdog (Tự phục hồi dịch vụ) hoạt động theo nguyên lý nào để đảm bảo hệ thống chạy 24/7?
▼
Watchdog là một tiến trình/dịch vụ độc lập chạy ngầm thực hiện 3 nhiệm vụ:
  • Giám sát trạng thái sống còn (Heartbeat & Service Controller): Định kỳ kiểm tra trạng thái của các tiến trình/dịch vụ nghiệp vụ (ví dụ qua System.ServiceProcess.ServiceController trên Windows). Nếu phát hiện service bị Stopped bất thường, Watchdog tự động kích hoạt lệnh Start lại.
  • Giám sát Telemetry phần cứng: Đo đạc mức chiếm dụng CPU, RAM, Disk. Nếu một tiến trình con bị treo hoặc rò rỉ bộ nhớ vượt ngưỡng an toàn trong thời gian dài, Watchdog sẽ kill tiến trình đó và khởi động lại một instance mới sạch sẽ.
  • Cảnh báo & Logging: Ghi lại toàn bộ lịch sử crash/restart vào hệ thống log để kỹ thuật viên điều tra nguyên nhân gốc rễ.
Câu 32: Sự khác biệt giữa Structured Logging (như Serilog) và Logging thông thường ra sao?
▼
  • Logging thông thường: Ghi log dạng chuỗi văn bản (Plain Text). Nhược điểm: rất khó tìm kiếm, lọc hoặc tổng hợp thông tin khi có hàng triệu dòng log.
  • Structured Logging (Serilog): Lưu log dưới dạng đối tượng có cấu trúc (JSON / Key-Value properties). Cho phép dễ dàng truy vấn chính xác theo từng thuộc tính (ví dụ: tìm tất cả log có OrderId = 123 hoặc ElapsedMs > 3000) và tích hợp mượt mà với các hệ thống phân tích log tập trung như Seq, ElasticSearch, CloudWatch.
Câu 33: Health Checks trong ASP.NET Core được cấu hình như thế nào và phân biệt Liveness vs Readiness?
▼
ASP.NET Core cung cấp sẵn services.AddHealthChecks() và endpoint /health để kiểm tra trạng thái kết nối tới Database, Caching, Cloud Storage:
  • Liveness Check: Kiểm tra xem ứng dụng có còn "sống" không. Nếu Unhealthy (chết/treo luồng), hệ thống điều phối (Watchdog / Kubernetes) sẽ restart ứng dụng.
  • Readiness Check: Kiểm tra xem ứng dụng đã sẵn sàng tiếp nhận traffic người dùng chưa (đã kết nối DB xong chưa, load cache xong chưa). Nếu Unhealthy, hệ thống tạm thời ngắt không điều phối traffic vào instance này nhưng không restart.
Câu 34: Em xử lý Exception trong ứng dụng .NET như thế nào để không làm gián đoạn hệ thống?
▼
  • Không dùng Exception cho các luồng điều khiển thông thường (Control Flow) vì chi phí tạo Stack Trace rất đắt đỏ. Sử dụng Result Pattern (Result<T>) cho các lỗi nghiệp vụ dự đoán được (Validation thất bại, không tìm thấy dữ liệu).
  • Chỉ ném (throw) Exception cho các lỗi bất thường hệ thống (lỗi mạng, mất kết nối DB).
  • Sử dụng GlobalExceptionMiddleware để bắt lỗi tập trung ở tầng biên, đảm bảo ứng dụng không bao giờ bị crash đột ngột và luôn trả về phản hồi chuẩn cho client. Khi re-throw exception, luôn dùng cú pháp throw; để bảo toàn Stack Trace gốc.

Chương 7: Cloud Storage (AWS S3) & Security

Câu 35: Em tích hợp và sử dụng AWS S3 trong ứng dụng .NET để giải quyết bài toán gì?
▼
Em sử dụng AWSSDK.S3 để lưu trữ các file báo cáo tài chính, file export dữ liệu, và media assets:
  • Giảm tải cho Database: Không lưu các file nhị phân lớn vào SQL Server, giúp kích thước file .mdf gọn nhẹ, backup và phục hồi CSDL cực nhanh.
  • Độc lập máy chủ: Ứng dụng Backend chạy stateless, không lo đầy ổ cứng máy chủ và dễ dàng mở rộng nhiều instance mà vẫn dùng chung kho file S3.
Câu 36: S3 Pre-Signed URL là gì? Tại sao nên dùng Pre-Signed URL khi upload / download file?
▼
Pre-Signed URL là một đường dẫn có chữ ký số mã hóa và thời hạn hết hạn xác định (ví dụ 15 phút), cho phép client truy cập trực tiếp vào một file riêng tư trên S3:
  • Bảo mật: Bucket S3 vẫn được giữ hoàn toàn ở chế độ Private (không public ra internet).
  • Tiết kiệm băng thông Backend: Trình duyệt web có thể upload hoặc download file trực tiếp với máy chủ của Amazon S3 mà không cần trung chuyển qua server backend của mình.
Câu 37: Làm thế nào để quản lý các thông tin cấu hình nhạy cảm (API Keys, Connection Strings, Secrets) an toàn?
▼
  • Tuyệt đối không commit Plain Text password, secret key lên Git repository.
  • Khi phát triển (Local): Dùng dotnet user-secrets hoặc appsettings.Development.json (đã thêm vào .gitignore).
  • Khi Production: Đọc từ Environment Variables (Biến môi trường) của hệ điều hành hoặc Secret Manager.
  • Đối với các API Key lưu trong CSDL: Sử dụng mã hóa đối xứng AES-256 hoặc Windows DPAPI để bảo vệ.
Câu 38: Em lưu trữ mật khẩu người dùng trong cơ sở dữ liệu như thế nào để đảm bảo an toàn?
▼
Tuyệt đối không mã hóa có thể giải mã được, mà sử dụng thuật toán băm (Hash) một chiều kèm Salt ngẫu nhiên bằng BCrypt (hoặc Argon2 / PBKDF2 của ASP.NET Core Identity). Cơ chế này chống lại các cuộc tấn công Rainbow Table và Brute-force ngay cả khi CSDL bị lộ.

Chương 8: Quy trình Agile / Scrum & Xử lý tình huống

Câu 39: Quy trình làm việc nhóm Agile/Scrum thực tế của em diễn ra như thế nào?
▼
Team của em làm việc theo Sprint 2 tuần:
  • Sprint Planning: Nhận User Stories từ Product Owner/Tech Lead trên Jira, thảo luận giải pháp kỹ thuật và estimate story points.
  • Daily Standup (15 phút mỗi sáng): Cập nhật tiến độ: hôm qua đã làm gì, hôm nay làm gì, và có gặp khó khăn (blocker) gì cần hỗ trợ không.
  • Code Review (Pull Request): Mọi code trước khi merge vào develop đều phải qua review về Clean Code, xử lý async, kiểm tra lỗi N+1 query và coverage Unit Test.
  • Sprint Retrospective: Họp tổng kết sau mỗi sprint để rút kinh nghiệm và cải tiến quy trình.
Câu 40: Khi đang làm việc trong Sprint mà có một lỗi nghiêm trọng (Hotfix) trên Production, em xử lý ra sao?
▼
  1. Thông báo ngay cho Tech Lead / Product Owner về mức độ ảnh hưởng của lỗi.
  2. Tạo nhánh hotfix/xxx từ branch main/production.
  3. Kiểm tra log Serilog để lấy thông tin lỗi, tái hiện chính xác lỗi trên môi trường staging/local.
  4. Sửa lỗi, bổ sung Unit Test để tránh tái phát (No Regression), review gấp với đồng nghiệp và deploy hotfix lên production.
  5. Merge ngược lại code hotfix vào branch develop để không bị mất code ở các bản release sau.
Câu 41: Khi gặp một bài toán kỹ thuật mới hoặc bug hóc búa chưa từng làm, em giải quyết như thế nào?
▼
Quy trình 4 bước của em:
  1. Khoanh vùng lỗi: Đọc log, kiểm tra Stack Trace và phân tích luồng dữ liệu.
  2. Tìm hiểu tài liệu: Đọc Official Docs của Microsoft / Amazon, kết hợp các công cụ hỗ trợ như AI để brainstorm các phương án khả thi.
  3. Thử nghiệm (PoC): Viết một đoạn code thử nghiệm nhỏ độc lập để kiểm chứng giải pháp trước khi áp dụng vào codebase chính.
  4. Kiểm thử & Đóng gói: Viết Unit Test bao phủ và chia sẻ giải pháp với team.
